A .wad, .wad.mem1 and .wad.vram share one layout: a little-endian header, then a TJZIP-compressed image of hash buckets and typed entries. The Wii loader (0x800f49d0) checks the HIG! magic, version 9, the size and the CRC-32, then decompresses the image in place.

Layout

Once decompressed, the image is laid out like this, with the header still at its start, so every offset counts from the start of the header:

OffsetSizeDescription
0x00000x80Header, little-endian
0x00800x10001024 hash buckets, a u32 entry offset each (0 = empty)
0x1080varEntries: a 0xC0-byte header, then the entry's data

Header (0x80 bytes)

OffsetSizeTypeDescription
0x004char[4]Magic HIG!
0x0468u32[17]First entry of each type list, types 0 to 16; 0 = none
0x484u32CRC-32 of the decompressed payload, started from register 0 (zlib.crc32(payload, 0xFFFFFFFF))
0x4C4u32Version, 9
0x504u32Decompressed payload size, not counting the header
0x544u32Compressed size; the TJZIP stream starts at 0x80
0x584u32Alignment the image is allocated on: 0x40 Wii, 0x80 PS3 and 3DS, 0x1000 Xbox 360
0x5C36-0, not read

The loader byte-swaps the header on big-endian consoles and allocates (size + 0x9F) & ~0x1F bytes for the image plus a 0x20020-byte margin. It reads (compressed size + 0x1F) & ~0x1F bytes into the margin, decompresses in place to image + 0x80, checks the size and CRC, and frees the margin.

Entry Header (0xC0 bytes, little-endian)

OffsetSizeTypeDescription
0x004u32Path hash (below)
0x0496char[96]Source path, NUL-padded, cut to 95 characters; not read
0x644u32Type; 25 is an alias
0x684u32Data size; 0 for an alias, which takes its target's at load
0x6C4offNext entry in the same hash bucket
0x704offNext entry in the same type list
0x744u32Entry index in image order
0x784u32Runtime: load state, 0 not loaded, 1 loaded, -1 loading or failed
0x7C4u32Runtime: the loaded object
0x804u320, not read
0x844u32Alias only: the target entry's offset minus 0x1080
0x8856-0, not read

The entry's data follows at +0xC0 in the platform's byte order. An alias copies its target's 0x7C and 0x68 at load (and 0x78 if its own is 0), then returns the target.

Path Hash

The CRC-32 of the source path below its platform folder (the part after ...\DATA\<platform>\), with a-z upper-cased and / turned into \.

Finding an Entry

  • By hash (0x800f4f20): the bucket is (hash & 0x3FF) ^ (type | type << 5), which equals (hash ^ 33 * type) & 1023 for every type in use. The chain is followed until an entry has the same hash and either the requested type or type 25. An alias sits in the bucket of its target's type.
  • By type (0x800f4ed0): from the head at 0x04, along the type-list links at 0x70.
  • Across WADs (0x800f2f80, 0x800f2e50): five slots, each searched as .wad then .wad.mem1.

Placement

The loader checks none of this, but every file follows it. Entry headers and data start on 64-byte boundaries. On PS3 all data starts on 128 bytes except shaders (type 10). On 3DS types 9, 13, 15 and 16 start on 128. On Xbox 360 the same four types put data + 0x80 on a 4 KB boundary, so .htx pixel data stored at offset 0x80 is page-aligned. Gaps are zero-filled. A WAD with no entries ends with 0xC0 zero bytes after the buckets.

When asked to, the loader runs a fixup (0x800f46f0): it walks the 17 type lists and the 1024 bucket chains, byte-swaps each entry's 0x00, 0x64, 0x68, 0x70, 0x74, 0x78 and 0x84 words, and turns the links into addresses.

TJZIP

An LZ77 variant with byte-aligned codes. The stream opens with a literal run, then alternates back-references and literals until the output reaches the stated size. Distances run from 1 to 32767 and copies may overlap.

Literal Run

A byte n. If it is non-zero, n + 2 literal bytes follow (3 to 257). If it is zero, a little-endian u16 count follows, then that many bytes.

Back-Reference

First byteBytesLengthDistancePost
0x00-0xBF2(b0 >> 5) + 4 (4-9)(b0 & 0x0C) << 6 | b1 (10 bits)b0 & 3
0xC0-0xDF3(b0 & 0x1F) + 4 (4-35)(b1 & 0xFC) << 6 | b2 (14 bits)b1 & 3
0xE0-0xFF, low nibble set3(b0 & 0x0F) + 3 (4-18)hi | (b1 & 0xFC) << 6 | b2b1 & 3
0xE0-0xFF, low nibble 0, b1 != 04b1 + 18 (19-273)hi | (b2 & 0xFC) << 6 | b3b2 & 3
0xE0-0xFF, low nibble 0, b1 == 06b2 << 8 | b3hi | (b4 & 0xFC) << 6 | b5b4 & 3

In the 0xE0 forms, hi = (b0 & 0x10) << 10 supplies distance bit 14. After each copy, post says what follows: 0 a literal run, 1 or 2 that many literal bytes and then another back-reference, 3 another back-reference straight away. OmegaStudio's compressor splits literal runs longer than 65,535 bytes with a zero-length back-reference (E0 00 00 00 00 01).

In OmegaStudio

  • Entries are found by walking every bucket chain and type list, and must be stored in their 0x74 index order. The CRC must match the decompressed image.
  • A path cut at 95 characters is restored when the hash proves it: the plugin tries the stored path with the tails of known names (.gdt.piece, .col.piece, .tuning.p2b, .animpack, .htx and the archive's own names) until one hashes to the entry.
  • An alias's target type is recovered from its bucket, ((bucket ^ hash) & 1023) / 33.
  • The platform comes from the stored paths, or else the alignment word: 0x40 Wii, 0x1000 Xbox 360, otherwise PS3.
  • Saving lays the entries out with the placement rules above, relinks the buckets and type lists, writes the version, sizes and CRC, and compresses with TJZIP. An untouched WAD saves byte for byte.
  • A WAD extracts to a folder of files plus a manifest of paths, hashes, types and aliases, and rebuilds from it. A new file takes the entry type of an existing file with the same extension.

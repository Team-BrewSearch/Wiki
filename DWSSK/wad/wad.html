A .wad, .wad.mem1 and .wad.vram share one layout. A level loads as a pair into one of five slots. The loader (0x800f49d0) checks the HIG! magic, version 9, the CRC-32 and size, then decompresses a TJZIP stream in place.

File Layout

+0x0000  0x0080    header (little-endian)
+0x0080  0x1000    1024 hash buckets, u32 each (0 = empty)
+0x1080  var       entries, each 0xC0-byte header + data

Header (0x80 bytes, little-endian)

OffsetSizeTypeDescription
0x004char[4]Magic HIG!; anything else is rejected
0x0468u32[17]First entry of each type list (types 0 to 16), as an offset into the image; 0 = none
0x484u32CRC-32 of the decompressed payload (zlib.crc32(payload, 0xFFFFFFFF))
0x4C4u32Version; must be 9
0x504u32Decompressed payload size
0x544u32Compressed size; the TJZIP stream starts at 0x80
0x584u32Alignment the loader allocates the image on: 0x40 Wii, 0x80 PS3/3DS, 0x1000 Xbox 360
0x5C400Not read

The loader reads the header, byte-swaps it on big-endian consoles, and allocates (size + 0x9F) & ~0x1F bytes for the image plus a 0x20020-byte margin. It reads (compressed size + 0x1F) & ~0x1F bytes into the margin, decompresses in place to image + 0x80, checks size and CRC, and frees the margin. The header stays at the start of the image, so every offset below counts from the start of the header.

Finding an Entry

Entries are found two ways:

  • By hash (0x800f4f20): the bucket is (hash & 0x3FF) ^ (type | type << 5), which equals (hash ^ 33 * type) & 1023 for the types in use. The chain is followed until an entry has the same hash and either the requested type or type 25.
  • By type (0x800f4ed0): from the head at 0x04, following the type-list links at 0x70 until an entry of that type.

Across WADs (0x800f2f80, 0x800f2e50): five slots, each searched as .wad then .wad.mem1.

Entry Header (0xC0 bytes, little-endian)

OffsetSizeTypeDescription
0x004u32Path hash: CRC-32 of the path below the platform folder, upper-cased, with backslashes
0x0496char[96]Source path, NUL-padded, cut to 95 characters; not read
0x644u32Type (table below); 25 is an alias
0x684u32Data size; 0 for an alias, which takes its target's at load
0x6C4u32Next entry in the same hash bucket
0x704u32Next entry in the same type list
0x744u32Entry index in image order; the fixup swaps it, nothing in the loader reads it
0x784u32Runtime: load state, 0 not loaded, 1 loaded, -1 loading or failed
0x7C4u32Runtime: the loaded object (an address or a handle)
0x804u320; not read
0x844u32Alias only: target entry's offset less 0x1080; fixup adds image address and 0x1080
0x88400Up to 0xC0; not read

The entry's data follows at +0xC0 in the platform's byte order. For an alias, the game copies the target's 0x7C, 0x68, and if its own is 0, 0x78, then returns the target.

Placement and Fixup

The loader checks none of this, but every file follows it: entry headers and data start on 64-byte boundaries. On the PS3 all data starts on 128 bytes except shaders (type 10). On the 3DS types 9, 13, 15 and 16 start on 128. On the Xbox 360 the same four types put data + 0x80 on a 4 KB boundary, so the pixels after a 0x80-byte .htx header are page-aligned. Gaps are zero-filled. A WAD with no entries ends with 0xC0 zero bytes after the buckets.

When asked to, the loader runs the fixup (0x800f46f0): it walks the 17 type lists and the 1024 bucket chains, byte-swaps each entry's 0x00, 0x64, 0x68, 0x70, 0x74, 0x78 and 0x84 words, and turns the list links into addresses.

Verified: Earlier passes ran the TJZIP decompressor (0x80095050) on buffers the plugin compresses, and the WAD path hash and lookup (0x800948b0, 0x800f4f20) on every Wii WAD.

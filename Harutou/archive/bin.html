Every data/*.bin file is a recursively nested table of contents. There is no magic number, no version field and no filenames: a table is a count, a list of offsets, and the payloads they point at. Children are often tables themselves, to varying depths.

File Layout

+----------------------+   <-- table base
| Count (4 bytes)      |       Number of child slots (u32 LE)
+----------------------+   <-- base + 4
| Offset Table         |       count * 4 bytes, relative to the table base
+----------------------+
| 0xFE Padding         |       up to the first child
+----------------------+
| Child Payloads ...   |       each aligned to 32 bytes
+----------------------+   <-- end of table

Table

OffsetSizeTypeDescription
0x004u32Child slot count
0x04count * 4u32[count]Child offsets, relative to this table's own base
varvaru8[]0xFE padding up to the first child
varvar-Child payloads, each aligned to a 32-byte boundary

The first offset is always >= 4 + count * 4, since it has to clear the header.

Slot Semantics

  • Offsets are relative to the table that lists them, not to the start of the file.
  • Offsets are not sorted.
  • Offsets may repeat. Two slots holding the same offset are aliases of one shared payload, not two copies.
  • An offset of 0 is an empty slot.
  • A child's length runs to the next larger distinct offset. The last child runs to the end of the parent.

Payload Identification

Leaves carry no names or type tags, so payloads are identified by magic bytes and structure: ringtex2, model, animation, Ogg and RIFF.

Note: An animation blob starts with a node count followed by per-node offsets, which is structurally indistinguishable from a table of contents. A recursive walk that does not recognise it first will descend into the clip and break it apart into individual bone tracks.

Unidentified Payloads

  • 0D 0A blobs - 40 to 96 byte blocks of 0D 0A followed by zeros, one at the end of most parent nodes. They hold no asset data and behave as end markers.

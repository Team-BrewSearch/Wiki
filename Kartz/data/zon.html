A .zon is a bundle of scenery models. Each model is a display list in exactly the format a TRK chunk uses. The layout below is the two-Kartz shape.

File Layout

+0x00  u32    model count
+0x04  u32    12, the size of this header
+0x08  u32    payload size, from +0x0C
+0x0C  u32[]  one absolute offset per model
model chunks, in table order
u32[3] per model, one 12-byte record each

Parser checks are exact: the model count is one or more, the header is 12 or 16 bytes, a wide header's spare word at +0x0C is zero, the stored payload length is at least four and no longer than the file minus 12, the offset table fits, each model offset lands after the table, and each offset holds a chunk. The trailer starts at the end of the last chunk, not at a stored offset.

The plugin reads the chunk shape off the chunk, so scenery chunks follow the same narrow and wide shapes a track chunk uses. Later model offsets can leave gaps the parser allows rather than requiring back-to-back chunks.

A chunk is a .trk chunk: a 24-byte header for the narrow shape, whose +0x04 is the prefix words plus the display list size and whose texture count is at +0x10, then that many texture references, then the display list. The wide shape's texture count is at +0x64 and its references are 16 bytes. The same interpreter runs over both, so .zon models draw, export to glTF and re-import through the same path a track does, textures included.

A chunk names its texture by slot, and the slot is resolved through the resource databases exactly as a track's is: the record that names the model carries a list of texture slots, and a slot's id sits either directly under name or one level down, under a texture list whose records hold the frames of an animated texture. A record can also name several models at once, and every skybox in a game shares one. Then the two lists run in parallel: the model at position i takes the texture at position i, one each, rather than all of them sharing the whole table. 119 models across the two games are paired that way, and the pairings agree with the names throughout, from SKY_ToothlessCove.zon to SKY_ToothlessCove.5tx down to mudblock.zon and mudblock.5tx. The display list is no help here: its TEXIMAGE_PARAM is a constant 0x40000000 with no size, format or address, all of which the game fills in when it binds the texture. Models that no resource database names fall back to the texture beside them, scored by how much of the name they share.

The block after the chunks is twelve bytes per model, not a fixed trailer: models/garage/garage.zon carries 156 bytes for its thirteen models, and all 116 bundles match the rule exactly. Its contents are carried through untouched. Positions stay inside the ±8 range a VTX_16 command can hold, so the models are authored small and placed by the code that loads them. Texture coordinates are in texels and are divided by the resolved texture's size to normalise them; all 116 bundles resolve a texture, and every one but the tiled water planes lands inside a span of eight.

Header Variants

The .zon header is 12 bytes or 16, the later one carrying a spare zero word. Chunk headers inside a bundle follow the narrow or wide shape the home page lists for track chunks.

Verification

  • Every shipped bundle, 116 in the two Kartz games, keeps the twelve-bytes-per-model rule for the block after the chunks.
  • Across all five games every one of the 588 .zon files reads, draws and re-serialises to the bytes it was read from.
  • glTF export and re-import unedited reproduces a scenery model byte for byte in 576 of 588 files. The rest are listed as known limits.

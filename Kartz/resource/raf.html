A .raf is the pointer-fixup table for the RDF of the same name. It carries no content of its own: every entry is the byte offset of a word inside the paired .rdf that holds a file offset and has to become a real address when the database is loaded. Both games ship one .raf beside every .rdf, and neither file is usable without the other.

File Structure

OffsetSizeTypeDescription
0x004u32Entry count
0x04count * 4u32[count]Byte offsets into the paired .rdf

The file is exactly 4 + 4 * count bytes, with no header, magic or padding.

Loading

The whole .rdf is read into one contiguous block, then each offset is patched in place. After that pass every pointer in the database is a live address.

for (u32 o : raf.offsets)
    *(u32*)(rdf + o) += (u32)rdf;

Rules

  • Every offset is a multiple of 4 and lands at least four bytes before the end of the paired .rdf. No offset appears twice.
  • Every word the table points at is itself a valid in-file offset, and never zero. There is no null-pointer encoding - a property with nothing to point at is omitted from its record instead.
  • The offsets are not sorted. They follow the order the writer emitted the records in, so a reader must not assume ascending order.
  • The words pointed at are not all 4-byte aligned, because string pointers address a byte-packed pool.
Rewriting: Anything that moves a record inside the .rdf invalidates both the stored offset and this table, and the pointer set cannot be recovered from the .rdf alone - a plausible file offset is indistinguishable from an integer property of the same magnitude. A rewritten database has to emit the .raf from the same pass that lays out the records.

An .rdf is a serialised object tree: records of named, typed properties. It names the files a level loads, the slot each of its textures fills and every value the level designer tuned. A TRK chunk's texture index points into a table this file holds. Each .rdf is paired with a RAF that lists its pointers.

The record format is the same in every game. This file split is the only real difference between the two Kartz games.

Layout

+----------------------+   <-- 0x00
| u32 dictionary       |       offset of the name dictionary
| u32 root             |       offset of the root record, 0x08 in retail files
+----------------------+   <-- 0x08
| Records              |       the object tree, in writer order
+----------------------+
| Arrays, vectors      |       out-of-line property values
+----------------------+
| Name dictionary      |
+----------------------+
| String pool          |       null-terminated ASCII
+----------------------+   <-- EOF

Both header words are pointers, so the RAF lists them as offsets 0 and 4.

Record

OffsetSizeTypeDescription
+0x004u32Property count
+0x048 * count{u32 key, u32 value}[]Properties, in authored order

A record is 4 + 8 * count bytes, with no class name, size or terminator. The key packs two dictionary indices:

BitsMeaning
16-31Property name index
0-15Type name index

Both index the same dictionary, so a property reads out as plain text: startdist of type fx32, model of type fileidlist. Type names are stored like any other name; only the way each type encodes its value is fixed.

Types

TypeStorageEncoding
fx32inline20.12 signed fixed point
fx16inlineFixed point in the low half of the slot
int32 / uint32inlineSigned / unsigned 32-bit
int16 / uint16inlineLow half of the slot
bool8inline0 or 255

lstringinlineLocalised string id, resolved against the files under loc

stringreferencedNull-terminated ASCII in the string pool
vector3fxreferencedThree 20.12 words
fileidlistreferencedOffset of a word that holds the offset of a fileid[]
T[]referencedArray of T, for every T above except vector3fx

A T[] value points at a u32 count followed by count four-byte elements, each encoded as that type would be inline. Elements of a referenced type are themselves pointers. An empty array is written as a lone zero word, not omitted.

fileidlist adds one hop: the slot points at a single word, and that word points at the u32 count. Otherwise it is the same as fileid[].

Name Dictionary

OffsetSizeTypeDescription
+0x004u32Name count
+0x044u32Offset of the key array
+0x084u32Offset of the string-offset array

The two arrays are count words long, parallel and contiguous, the string array starting right after the key array. Entry i pairs key i with string i. Keys are in ascending order, so lookup is a binary search. Entry 0 is the empty string with key 0. Dictionaries hold 54 to 1942 names.

Unknown: how a key is derived from its name. It is a pure function of the string, since a name carries the same key in every file, and the empty string maps to 0 while a single character maps to its own byte value. It is not CRC-32 under any common polynomial, not Jenkins one-at-a-time, and not a multiply-accumulate chain in either direction. Reading never needs it, and existing names carry through unchanged; only a brand-new name would.

Texture Slot Table

A track's textures live in its record's textures property: a record holding a texture array. The array index is the slot number a TRK stores, and the table is written out in full, empty slots included. Each element is a seven-property record:

PropertyTypeMeaning
namefileid[]The .5tx files bound to the slot. Empty for an unused slot; several for an animated slot, played in order
animationframetimefx32Seconds per frame
texturesizeinvfx32Reciprocal of the texture size, for the UV scale
animationtypeint320 for a still texture
loopmodeint32Unknown
updatemodeint32Unknown
pixelintervalint32Unknown

Measured on all 28 tracks of the two Kartz games:

  • Slot 0 is always empty, which is why a TRK's stored texture index is never 0.
  • No track draws a slot whose name list is empty, and every table is longer than the highest slot its track draws.
  • The table is not a permutation. One fileid can fill several slots: Madagascar's FoosaRocks binds FR_fast_rock to slots 3 and 4, FR_grass_tile to 5 and 8, and FR_fast_mud to 1 and 7.

Track Subtree

Each entry of trackarray holds nameid, an env record, the track itself and a trackobject list.

PathTypeContents
track.modelfileidlistFour ids in fixed order: the .col, the .trk, the .bpvs, then -1. The only place a track's geometry file is named
track.textures.textureresource[]The slot table
track.billboardobject.allbillboardobjectsresource[]Scenery billboards
track.dynamicobject.alldynamicobjectsresource[]Animated scenery
track.startdist, deltaforwarddist, deltasidedistfx32Start-grid spacing, from which the grid is generated
trackobject.alltrackobjectsresource[]Gameplay props, each with tracksectionindex, type, sidedistance, fowarddistance and height

A billboard is a full placement: x, y, z, width, height, scalex, scaley, scaletime, movedirection, movespeed, moveheight and a texture fileid. It names its texture by archive id, not by slot, so billboard textures never appear in the slot table.

A dynamic object adds movetype, rotation and up-down motion, four texture-scroll values, renderborder, vertexalphavalue, a model fileid naming a .zon, and a textures record of its own.

Root

Super Star Kartz's main.rdf opens with sound, boot, loc, tracks, ai, cars, menusetting, sfx, gameplay, lotcheck, driveranimations, weaponanimations, weapons and skybox. Madagascar's adds test, menus and huds. A per-track file's root is a single trackarray with one entry.

tracks also carries txvram and plvram, two int32[] holding the texture and palette VRAM budgets, and trackobjectconfig.

In OmegaStudio

The plugin reads every .rdf beside the archive, in path order, skipping files it cannot read. If none parses, track textures fall back to a name match (see 5TX).

  • The file must hold the 8-byte header. The dictionary and its string-offset array must fit the file, every string offset must point inside it, and a name is read up to 128 bytes.
  • Each record offset is read once, so two pointers to one record give the same object. Records nest at most 64 levels deep. A record with a property that fails to read fails as a whole.
  • Only resource, resource[], fileid, fileid[] and fileidlist are followed. Every other type is kept as its raw 32-bit slot.
  • Texture slots come from any record that carries both a model id list and a textures table, given as a resource[] or as a record with a texture array. A slot's ids come from its own name list or from the name lists of nested texture records, up to three levels down.
  • When a record names several models and its table has exactly as many entries, the two lists pair up: model i gets entry i as its only slot. Every skybox in a game is bound this way.
  • The RDF is never written.

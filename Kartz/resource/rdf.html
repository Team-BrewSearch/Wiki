An .rdf is a serialised object tree: records of named, typed properties. It names the files a level loads, the slot each of its textures occupies, and every tunable the level author set. A TRK's texture index indexes a table this file holds outright.

Each is paired with a RAF holding its pointer-fixup table. This split is the only substantive difference between the two games.

File Layout

+----------------------+   <-- offset 0
| u32 dictionary       |       pointer to the name dictionary
| u32 root             |       pointer to the root record (always 0x08)
+----------------------+   <-- 0x08
| Records              |       the object tree, in writer order
+----------------------+
| Arrays, vectors      |       out-of-line property payloads
+----------------------+
| Name dictionary      |
+----------------------+
| String pool          |       null-terminated ASCII
+----------------------+   <-- EOF

Both header words are relocated, so they appear in the RAF as offsets 0 and 4.

Record

OffsetSizeTypeDescription
+0x004u32Property count
+0x04count * 8{u32 key, u32 value}[]Properties, in authored order

A record is 4 + 8 * count bytes, with no class name, size or terminator. The key packs two dictionary indices:

BitsMeaning
0-15Type name index
16-31Property name index

Both index the same dictionary, so a property reads out as plain text - startdist of type fx32, model of type fileidlist. Type names are stored in the file like any other name; nothing is hardcoded except how each named type encodes its value.

Types

An inline type stores its value in the 32-bit slot. A referenced type stores a file offset there, and that slot appears in the RAF. The distinction is exact, so the type name alone tells a reader whether to dereference.

TypeStorageEncoding
fx32inline20.12 signed fixed point
fx16inlineFixed point, low half of the slot
int32 / uint32inlineSigned / unsigned 32-bit
int16 / uint16inlineLow half of the slot
bool8inline0 or 255
fileidinlineIndex into the GDF path table
lstringinlineLocalised-string id, resolved against the files under loc
resourcereferencedNested record
stringreferencedNull-terminated ASCII in the string pool
vector3fxreferencedThree 20.12 words
fileidlistreferencedPointer to a pointer to an array - see below
T[]referencedArray of T, for every T above except vector3fx

Every T[] value points at a u32 count followed by count four-byte elements, each encoded as that element type would be inline. For referenced element types the elements are themselves relocated pointers. An empty array is written out as a lone zero word rather than omitted.

fileidlist carries one extra hop: the property slot points at a single relocated word, and that word points at the u32 count. It is otherwise identical to fileid[].

Name Dictionary

OffsetSizeTypeDescription
+0x004u32Name count
+0x044u32Pointer to the key array
+0x084u32Pointer to the string-offset array

Both arrays are count words long and parallel: entry i pairs key i with the string at offset i. They are contiguous, the string array starting immediately after the key array. Keys are stored in ascending order, so lookup is a binary search. Entry 0 is the empty string with key 0. Dictionaries run from 54 names to 1942.

Not reverse-engineered: how a key is derived from its name. It is a pure function of the string - a name carries the same key in every file - and the empty string hashes to 0 while a single character hashes to its own byte value. It is not CRC-32 under any common polynomial, not Jenkins one-at-a-time, and not a multiply-accumulate chain in either direction. Reading and rewriting a database does not need it: existing keys carry through unchanged, and only a brand-new name would require computing one.

The Texture Slot Table

A track's textures live at track.textures.texture, a resource[] whose array index is the slot number a TRK names. The table is written out in full, empty slots included.

Each element is a seven-property record:

PropertyTypeMeaning
namefileid[]The .5tx files bound to this slot. Empty for an unused slot; more than one for an animated slot, played in order
animationframetimefx32Seconds per frame
texturesizeinvfx32Reciprocal of the texture size, for the UV scale
animationtypeint320 for a still texture
loopmodeint32
updatemodeint32
pixelintervalint32

Three rules hold on all 28 tracks in the two games:

  • Slot 0 is always empty, which is why a TRK's texture index is never 0.
  • No track draws a slot whose name list is empty, and every table is longer than the track's highest drawn slot - tables carry entries the geometry never references.
  • The table is not a permutation. The same fileid can appear in several slots: Madagascar's FoosaRocks binds FR_fast_rock to slots 3 and 4, FR_grass_tile to 5 and 8, FR_fast_mud to 1 and 7.

Track Subtree

Each entry of trackarray holds nameid, an env record, the track itself and a trackobject list.

PathTypeContents
track.modelfileidlistFour ids in a fixed order: the .col, the .trk, the .bpvs, then -1. The only place a track's geometry file is named
track.textures.textureresource[]The slot table above
track.billboardobject.allbillboardobjectsresource[]Scenery billboards
track.dynamicobject.alldynamicobjectsresource[]Animated scenery
track.startdist, deltaforwarddist, deltasidedistfx32Start-grid spacing, from which the grid is generated
trackobject.alltrackobjectsresource[]Gameplay props, each with tracksectionindex, type, sidedistance, fowarddistance and height

A billboard is a full authored placement - x, y, z, width, height, scalex, scaley, scaletime, movedirection, movespeed, moveheight, and a texture fileid. It names its texture by archive id, not by slot, so billboard textures never appear in the slot table.

A dynamic object adds movetype, rotation and up-down motion, four texture-scroll parameters, renderborder, vertexalphavalue, a model fileid naming a .zon, and its own nested textures record.

Root

Super Star Kartz's main.rdf opens with sound, boot, loc, tracks, ai, cars, menusetting, sfx, gameplay, lotcheck, driveranimations, weaponanimations, weapons and skybox; Madagascar's adds test, menus and huds. A per-track file's root is a single trackarray holding one entry.

tracks also carries txvram and plvram, two int32[] giving the texture and palette VRAM budgets, and trackobjectconfig.

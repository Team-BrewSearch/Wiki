.bpvs holds the visibility data for one track: which TRK chunks to draw from each sector of its paired COL surface. The detail below is measured on the two Kartz games.

File Layout

+0x00  u32    sector count, matching the .col
+0x04  u32    8, the offset of the table below
+0x08  u32[]  one absolute offset per sector
       u32    zero terminator
run lists, packed back to back

A list is a sequence of bytes. The low seven bits are a run length; bit 7 set means those chunks are skipped, clear means they are drawn. A list ends when its runs cover the track's chunk count, which is why the lists are self-terminating and several sectors can share one. A run longer than 127 chunks is split across bytes of the same kind.

The plugin takes the track's chunk count from the paired .trk file, so a .bpvs decodes only beside the track whose count it names. The table checks are exact: the word at +0x04 is 8, the sector count is one or more and at most 8192, the terminator after the table is zero, every sector offset lands after the table and inside the file, and each run list covers the chunk count exactly. A list that runs past the end of the file fails with its offset, and a list that covers the wrong count fails with the count and the track's chunk count.

Across the shipped tracks a sector draws between a third and three quarters of the chunks.

Run Lists and Orphans

Four tracks carry a well-formed run list that no sector points at, a leftover from whatever built them, covering the chunk count exactly like any other list. Reading a file keeps only the lists the table names, and writing one back preserves every byte, orphans included; rebuilding a table from scratch drops them.

Rebuild

Decoding and re-encoding a .bpvs reproduces the same visible chunk set. The writer keeps the run lists byte for byte when it is handed the decoded model, so only a table built from scratch loses an orphan list.

Verification

  • All 28 two-Kartz visibility files decode and re-encode to the same visible chunk set.
  • Across all five games the plugin reads 115 .bpvs files. The 29 Monster Jam files are a 12-byte stub with no run lists to read.
  • The section count has to agree across the .col table, the .bpvs sector list and the .trk header.

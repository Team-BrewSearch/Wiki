.bpvs is one track's visibility data: for each sector of the paired COL surface, which TRK chunks to draw. The figures below are measured on the two Kartz games.

Run Lists

A run list is a sequence of bytes. The low seven bits are a run length; bit 7 set means those chunks are hidden, clear means they are drawn. A list ends once its runs cover the track's chunk count, so lists need no terminator and several sectors can share one. A run longer than 127 chunks is split across bytes of the same kind.

A sector draws between a third and three quarters of a track's chunks.

Four tracks carry a well-formed run list that no sector points at, left over from whatever built them.

In OmegaStudio

  • The chunk count comes from the .trk with the same path and name, so a .bpvs decodes only beside its track.
  • The file is at least 16 bytes, the word at +0x04 is 8, the sector count is 1 to 8192, the table and terminator fit, the terminator is zero, and every list offset lands after the table and inside the file.
  • Each list must cover the chunk count exactly. A list that runs off the end of the file fails with its offset; one that covers the wrong count fails with both counts.
  • The Properties pane shows the sector count, the average and range of chunks drawn, and how many lists are shared.
  • Writing back an unchanged file keeps every byte, orphan lists included. A table built from scratch drops them.

All 28 Kartz visibility files decode and re-encode to the same visible chunk set. Monster Jam's 29 files are 12-byte stubs with no lists.

A .trk file holds one track's geometry as pre-built Nintendo DS GX display lists, split into chunks. The header is followed by two parallel per-chunk tables, then the chunks themselves, then a run of tail sections the engine reads at load time.

File Layout

+----------------------+   <-- offset 0
| File header          |       56 bytes (0x38)
+----------------------+   <-- 0x38
| Chunk offset table   |       numTotal * u32, absolute file offsets
+----------------------+   <-- 0x38 + numTotal*4
| Chunk position table |       numTotal * 12 bytes, i32 x/y/z in 20.12
+----------------------+
| Display list chunks  |       the bulk of the file
+----------------------+
| Tail sections        |       one contiguous run, five header offsets
+----------------------+   <-- EOF

Counts sit immediately before the offset they belong to for the sections at 0x24, 0x2C and 0x34. The section at 0x14 takes its count from 0x00 instead, and the section at 0x1C has no count in the header at all. A zero offset means the section is absent, not that it lives at offset 0.

The field at 0x06 is a cached entry point into the region table, not an independent value, which is why it reads as an arbitrary small number. A track and its _Reverse variant can store different indices that resolve to the same world position.

Chunk Offset Table

numTotal absolute file offsets, one per chunk. Each can point anywhere in the file that holds a valid chunk.

Chunk Position Table

numTotal records of three i32 in 20.12 fixed point: the chunk's world-space centre. A chunk's MTX_TRANS is always exactly this value.

Chunk Header (24 bytes)

OffsetSizeTypeDescription
+0x002u16Chunk index - equal to the chunk's own position in the offset table
+0x022u16Chunk type - 0x000E primary, 0x0000 detail, 0x0013 on 12 chunks only
+0x044u32dlSize - display list byte length following this header, always a multiple of 4
+0x084u32coord_scale - a duplicate of this chunk's own MTX_SCALE parameter, in the same raw 20.12 form
+0x0C4u32Bounding radius of the chunk's geometry, 20.12 fixed point, in world units
+0x104u32texCount - number of texture reference entries following
+0x144u32Always 0

Primary chunks always sort first in the offset table: FarFarAway's 388 chunks are 87 primaries at indices 0-86 followed by 301 detail chunks.

The bounding radius at +0x0C tracks half the diagonal of the chunk's vertex bounding box very closely and never exceeds it - the exporter fits a sphere, in fixed point. Treat it as a radius rather than expecting to recompute it exactly from decoded vertices.

Chunk type 0x0013 appears only in ShippingFreighter, in both games. Every one of the 12 has texCount == 1, an unusually large coord_scale of 8, 16 or 32, and a radius of 48 to 177 world units; they are the freighter's hull slabs. What the type changes at draw time is not known.

Texture Reference Entries

texCount entries of 12 bytes follow the chunk header.

OffsetSizeTypeDescription
+0x004u32Display-list-relative byte offset of a TEXIMAGE_PARAM opcode's parameter word
+0x044u32Display-list-relative byte offset of the same group's PLTT_BASE parameter word
+0x084u32Texture slot index. Never 0

Texture selection is resolved purely through this table. Every real TEXIMAGE_PARAM value in the display list is exactly 0x40000000 - texcoord-transform mode set, every VRAM offset, size and format bit zero - which is not a valid standalone hardware texture setup. The engine patches the real VRAM address, format and size into that opcode at load time using this table.

The index addresses track.textures.texture in the level's RDF directly: index n is array element n. Slot 0 is empty in every shipped track, which is why the index is never 0.

Tail Sections

The five offsets at 0x14, 0x1C, 0x24, 0x2C and 0x34 point into one contiguous run of tail data at the end of the file. The non-zero offsets increase monotonically and the last section runs to the end of the file. Record sizes divide the sections exactly.

Region table at 0x34

The section begins with its own table of count absolute file offsets addressing the 32-byte records that follow. They are contiguous, strictly ascending, and the first is always sectionStart + count * 4.

Each record is eight i32, of which only three are ever non-zero:

WordDescription
1A chunk index, distinct across the table
2A chunk count
7The record's own index in the table

Tracks carry 9 to 19 regions. The counts in word 2 sum to the primary chunk count on 15 of the 28 tracks and fall 1 to 6 short on the rest, so the table partitions a track's primary chunks into regions with a few left over on the larger tracks.

Rewriting: Any change to the file's size invalidates the region table's internal offsets as well as the five header offsets, so a rewrite has to shift both. At an identical size the stale pointers stay accidentally correct, which hides the problem.

Not every in-range word in the tail is a pointer: some fields hold 20.12 coordinates whose raw values land in the same numeric range. In FarFarAway's section at 0x2C, two records contain 0x21000, simultaneously the address 135168 and the coordinate 33.0. They are coordinates - as addresses they would land mid-record inside the section at 0x1C, and the surrounding fields read as a heading of 180.0 with mirrored X positions of plus and minus 7.0.

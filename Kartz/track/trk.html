A .trk file holds one track's geometry as pre-built Nintendo DS GX display lists, split into chunks. The header is followed by two parallel per-chunk tables, then the chunks themselves, then a run of tail sections the engine reads at load time.

File Layout

+----------------------+   <-- offset 0
| File header          |       56 bytes (0x38)
+----------------------+   <-- 0x38
| Chunk offset table   |       numTotal * u32, absolute file offsets
+----------------------+   <-- 0x38 + numTotal*4
| Chunk position table |       numTotal * 12 bytes, i32 x/y/z in 20.12
+----------------------+
| Display list chunks  |       the bulk of the file
+----------------------+
| Tail sections        |       one contiguous run, five header offsets
+----------------------+   <-- EOF

File Header (56 bytes)

OffsetSizeTypeDescription
0x002u16Visibility section count - equals the primary chunk count on 10 of 16 tracks and is one higher on the other 6. Also the entry count of the section at 0x14
0x022u16numTotal - chunk count
0x042u16Duplicate of numTotal, equal on all 16 tracks
0x062u16Not reverse-engineered - a small per-track value (1, 4, 12, 20, 37, 55, 57, 91, 103, 104, 109), near-identical between a track and its _Reverse variant. Not any texture, chunk or section count
0x084u32Always 0
0x0C4u32Chunk offset table start - always 0x38
0x104u32Chunk position table start - always 0x38 + numTotal * 4
0x144u32Section offset: vertex-colour palette
0x184u32Entry count for the section at 0x1C. Zero on all 16 tracks
0x1C4u32Section offset: texcoord-transform params
0x204u32Entry count for the section at 0x24
0x244u32Section offset: track-section defs
0x284u32Entry count for the section at 0x2C
0x2C4u32Section offset: material data
0x304u32Entry count for the section at 0x34
0x344u32Section offset: spatial BVH, running to the end of the file

Each count sits before the offset it belongs to, so the pairing is (count at X - 4, offset at X). A zero offset means the section is absent, not that it lives at offset 0.

Chunk Offset Table

numTotal absolute file offsets, one per chunk. Nothing requires the position table, or anything else, to follow immediately - each offset can point anywhere in the file that holds a valid chunk.

Chunk Position Table

numTotal records of three i32 in 20.12 fixed point: the chunk's world-space centre. A chunk's MTX_TRANS is always exactly this value, never an independently recomputed bounding-box centre.

Chunk Header (24 bytes)

OffsetSizeTypeDescription
+0x002u16Chunk index - equal to the chunk's own position in the offset table across all 3996 chunks
+0x022u16Chunk type - 0x000E primary, 0x0000 detail, 0x0013 on 12 chunks only
+0x044u32dlSize - display list byte length following this header, always a multiple of 4
+0x084u32coord_scale - a duplicate of this chunk's own MTX_SCALE parameter, in the same raw 20.12 form
+0x0C4u32Not reverse-engineered - see below
+0x104u32texCount - number of texture reference entries following
+0x144u32Always 0, across all 3996 chunks

Primary chunks always sort first in the offset table: FarFarAway's 388 chunks are 87 primaries at indices 0-86 followed by 301 detail chunks. The 0x0013 type appears on 4 chunks in Super Star Kartz's ShippingFreighter and 8 across Madagascar Kartz's ShippingFreighter pair, and nowhere else in either game; what distinguishes it is not known.

coord_scale equals the chunk's emitted MTX_SCALE in all 3988 non-empty chunks across all 16 tracks, with zero exceptions - the remaining 8 chunks carry no display list. Values are therefore clean powers of two: 0x2000, 0x4000, 0x8000 and so on.

The field at +0x0C is bounded but undecoded. It occupies exactly bits 0-22 (archive-wide OR of 0x007FFFFF, 20 to 23 bits per track), is never zero in any of the 3996 chunks, and is mostly unique with 2771 distinct values. It is provably not the vertex count, triangle count, dlSize, chunk position or bounding box, and it is not monotonic in chunk index. Its popcount is bell-shaped around 9 of 23, which fits either a precomputed visibility bitmask or a spatial hash; the data alone cannot separate the two. It shows no correlation with geometry.

Texture Reference Entries

texCount entries of 12 bytes follow the chunk header.

OffsetSizeTypeDescription
+0x004u32Display-list-relative byte offset of a TEXIMAGE_PARAM opcode's parameter word
+0x044u32Display-list-relative byte offset of the same group's PLTT_BASE parameter word
+0x084u32Texture index, 1-based. Never 0 in any shipped chunk

Texture selection is resolved purely through this table. Every real TEXIMAGE_PARAM value in the display list is exactly 0x40000000 - bit 30, texcoord-transform mode, set, with every VRAM offset, size and format bit zero, which is not a valid standalone hardware texture setup. The engine evidently patches the real VRAM address, format and size into that opcode at load time using this table.

The index is into the level's texture slot table, which the TRK does not contain - see RDF.

Tail Sections

The five offsets at 0x14, 0x1C, 0x24, 0x2C and 0x34 point into one contiguous run of tail data at the end of the file. On every shipped track the non-zero offsets increase monotonically and the last section runs to the end of the file. What the records mean is not reverse-engineered; their framing is.

SectionFraming
0x14u16[count at 0x00], 4-byte aligned. Values are RGB555, 0x7FFF being white - a per-section colour table
0x1C16-byte records. Leading u16 fields are small counts; the trailing pair is 20.12 fixed-point bounds
0x24count at 0x20 records of 32 bytes (FarFarAway 52 x 32 = 1664, IsleOfBerk 44 x 32 = 1408)
0x2Ccount at 0x28 records of 28 bytes, holding 20.12 positions and headings (FarFarAway 4 x 28 = 112)
0x34u32 offsets[count at 0x30] followed by count records of 32 bytes (12 x 4 + 12 x 32 = 432; GallaxharsShip 11 x 4 + 11 x 32 = 396)
Note: The section at 0x34 begins with its own table of absolute file offsets, count of them read from 0x30, addressing the records that follow. Verified on all 16 tracks: contiguous, strictly ascending, all in-file, and the first entry always exactly sectionStart + count * 4. Any change to the file's size invalidates all of them, so a rewrite has to shift both the five header offsets and this internal table. At an identical size the stale pointers stay accidentally correct, which hides the problem.

Not every in-range word in the tail is a pointer: some fields hold 20.12 coordinates whose raw values land in the same numeric range. In FarFarAway's section at 0x2C, two records contain 0x21000, simultaneously the address 135168 and the coordinate 33.0. They are coordinates - as addresses they would land mid-record inside the section at 0x1C, and the surrounding fields read as a heading of 180.0 with mirrored X positions of plus and minus 7.0.
